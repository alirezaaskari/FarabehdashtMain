# ADR-0001 — پشته فنی و بستر اجرا

- **وضعیت:** تأییدشده (مدیر، مسیر A)
- **تاریخ:** 1404 / 2026-09
- **جایگزینِ:** تصمیم قبلی مبنی بر ساخت روی وردپرس

## زمینه

پروژه از وردپرس خارج می‌شود و کدمحور بازنویسی می‌شود. بستر میزبانی موجود **cPanel** است.
گزینه Next.js بررسی و رد شد، چون روی cPanel با محدودیت اینود، RAM مرحله Build، خواب‌رفتن
پروسه Passenger و نبود PostgreSQL روبه‌رو می‌شود.

### بررسی‌های عملی انجام‌شده هنگام پیاده‌سازی بخش ۱

* **Laravel 13 + Filament 5:** سازگاری با `composer require --dry-run` تأیید شد
  (Filament v5.8 روی Laravel 13 حل می‌شود). ADR قبلاً Laravel 12 و Filament 4 نوشته بود؛
  چون نسخه پایدار فعلی ۱۳ است و PHP هاست آن را پوشش می‌دهد، به ۱۳ به‌روز شد.
* **spatie/laravel-permission 8.3** روی Laravel 13 حل می‌شود.
* **تاریخ شمسی بدون وابستگی:** افزونه `intl` با
  `IntlDateFormatter('fa_IR@calendar=persian', …)` خروجی درست می‌دهد
  (آزمون: `۲۸ شهریور ۱۴۰۵`). بنابراین `morilog/jalali` حذف شد — یک وابستگی کمتر.
* **Pest به‌جای PHPUnit انتخاب نشد:** Pest 5 نیازمند PHPUnit 13 است در حالی‌که اسکلت
  Laravel روی PHPUnit 12 قفل است، و `laravel/pao` با Pest 4 تعارض دارد. PHPUnit همراه
  خود Laravel بدون هیچ تعارضی کار می‌کند و برای این پروژه کافی است. در صورت نیاز، بعداً
  قابل تعویض است بدون تغییر در تست‌ها (تست‌ها کلاس‌های استاندارد PHPUnit هستند).

## دلایل

1. **بومی بودن با cPanel** — PHP-FPM بدون مدیریت پروسه، بدون Build سنگین، بدون مصرف اینود بالا.
2. **سئو** — صفحات عمومی سمت سرور رندر می‌شوند؛ بدون هیدراسیون و بدون JS اجباری.
3. **پنل مدیریت** — Filament همان «مدیریت بدون کدنویسی» را می‌دهد که تنها مزیت واقعی وردپرس بود.
4. **اکوسیستم ایرانی** — درگاه‌های شتاب، ملی‌پیامک و تاریخ شمسی در PHP آماده و بالغ‌اند.
5. **یک کدبیس** — سایت عمومی، میزکار کاربر و پنل مدیر در یک اپ؛ بدون مرز شبکه‌ای اضافه.

## چرا SPA (Inertia/Vue/React) برای بخش عمومی انتخاب نشد

صفحات عمومی محصول (دانشنامه، بانک مواد شیمیایی، آگهی‌ها) باید سبک، ایندکس‌پذیر و روی
هاست اشتراکی سریع باشند. Blade این را بدون هزینه Build و بدون ریسک سئو می‌دهد.
جاهایی که تعامل سنگین دارند (ابزارهای محاسباتی، فرم چندمرحله‌ای رزومه) با Alpine.js یا
یک کامپوننت Livewire موضعی پوشش داده می‌شوند، نه با بازنویسی کل لایه نمایش.

- جست‌وجوی معنایی برداری (pgvector) در نسخه ۱ در دسترس نیست. نسخه ۱ با Full-text دیتابیس

## PHPStan — اجرای واقعی (بخش ۳)

تا پایان بخش ۲ تحلیل ایستا هرگز به‌صورت محلی اجرا نشده بود، چون دانلود بسته از
`codeload.github.com` در محیط ساخت ۴۰۳ می‌گیرد. این ریسک باز ثبت شده بود.

راه‌حل: خود `github.com` روی پروتکل git در دسترس است، فقط آرشیو zip مسدود است.
پس بسته‌ها از git کلون و به‌صورت مخزن `path` موقت نصب شدند؛ `composer.json` و
`composer.lock` پروژه دست‌نخورده ماندند و CI مثل همیشه از packagist نصب می‌کند.

اولین اجرای واقعی سطح ۶، **سیزده ایراد** پیدا کرد که همه اصلاح شدند:

| ایراد | ماهیت | اصلاح |
|---|---|---|
| `checkMissingIterableValueType` در `phpstan.neon` | این کلید در PHPStan ۲ حذف شده و پیکربندی را نامعتبر می‌کرد — یعنی تحلیل اصلاً اجرا نمی‌شد | برداشته شد |
| ۶ مورد «دسترسی به ویژگی تعریف‌نشده» روی `User`، `OtpCode` | مستندنبودن ستون‌ها | `@property` کامل برای هر سه مدل نوشته شد |
| نوع بازگشتی عمومی `activeProfiles()` | نامشخص‌بودن `Collection<int, UserProfile>` | نوع دقیق اعلام شد |
| `str_replace` با آرایه عدد صحیح در `Mobile` | تکیه بر تبدیل ضمنی نوع | ثابت `LATIN_DIGITS` از رشته ساخته شد |
| `array_values` روی چیزی که از قبل list است | کد بی‌اثر | حذف شد |
| ۵ مورد `env()` بیرون از `config/` در پیکربندی ماژول | **هشدار نادرست** | با `ignoreErrors` محدود به `app/Modules/*/config/*.php` و با دلیل مکتوب کنار گذاشته شد |

درباره مورد آخر: `mergeConfigFrom` وقتی پیکربندی کش شده باشد اصلاً فایل را
نمی‌خواند (`ServiceProvider::mergeConfigFrom`، خط ۱۶۵)، پس `env()` در پیکربندی
ماژول دقیقاً مثل `env()` در `config/` رفتار می‌کند. قاعده larastan فقط مسیر فایل
را می‌بیند و قرارداد ماژولی ما را نمی‌شناسد.

**نتیجه:** `composer run check` — هر سه مرحله سبز.


## بازنگری نسخه PHP — از ۸٫۳ به ۸٫۴ (هنگام استقرار)

### چه شد

تصمیم اولیه (A-01) PHP ۸٫۳ بود. هنگام اولین استقرار روی سرور، `composer install`
شکست خورد:

```
symfony/console v8.1.7 requires php >=8.4.1
-> your php version (8.3.33) does not satisfy that requirement.
```

### علت ریشه‌ای — یک ایراد در پیکربندی پروژه

`composer.json` می‌گفت `"php": "^8.3"`، ولی Composer هنگام حل وابستگی‌ها
**نسخه PHP محیطی که در آن اجرا می‌شود** را مبنا می‌گیرد، نه محدودیت اعلام‌شده
را. محیط ساخت PHP ۸٫۴ داشت، پس `composer.lock` با بسته‌هایی پر شد که PHP ۸٫۴
می‌خواستند — و روی سرور ۸٫۳ اصلاً نصب نمی‌شد.

این ایراد تا لحظه استقرار دیده نشد، چون همه تست‌ها روی همان محیط ۸٫۴ سبز بودند.

### اصلاح

```json
"config": {
    "platform": { "php": "8.4.1" }
}
```

با این قفل، `composer.lock` همیشه برای نسخه هدف حل می‌شود، فارغ از اینکه
توسعه‌دهنده چه نسخه‌ای دارد. **این اصلاح مستقل از انتخاب ۸٫۳ یا ۸٫۴ لازم بود.**

### تصمیم نسخه

مدیر ترجیح داد به‌جای پایین‌آوردن بسته‌ها، نسخه PHP هاست را بالا ببرد.
سرور `h9` نسخه `ea-php84` را داشت و دامنه `farabehdasht.com` در MultiPHP Manager
روی آن تنظیم شد: **PHP 8.4.25**، با همه افزونه‌های لازم و `memory_limit` دو
گیگابایت.

گزینه دیگر، نگه‌داشتن ۸٫۳ و بردن PHPUnit به ۱۲ و Symfony به ۷٫۴ بود. آن هم
درست کار می‌کرد، ولی یک نسخه عقب‌تر می‌ماند بدون اینکه چیزی به‌دست بیاید.

### نکته عملیاتی

مجموعه افزونه‌های PHP در سی‌پنل **برای هر نسخه جداست**. پس از تغییر نسخه،
`intl` و بقیه دوباره بررسی شدند — بدون `intl` تاریخ شمسی کار نمی‌کند.
